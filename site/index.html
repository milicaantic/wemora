React web app → Expo mobile app

Port the app. Prove every screen.

Wemora rewrites a React single-page app as an Expo app, one screen at a time. A screen gets into the app only after the tests written against the web original pass on the phone build, unchanged.

How a run works

Agents write the code. Tests decide what stays.

Each step is a Mozaik participant. Agents get a fresh context per task, events carry only IDs, and the shared board holds the plan, tests and results.

  1. Analyze

    Parse routes, imports and web-only APIs, then describe every screen with its exact texts.

    analyzer · haiku-4-5

  2. Plan

    Split the app into screens and shared units, with obligations each screen must still meet.

    architect · sonnet-4-6

  3. Scaffold

    Create an empty Expo app with one route per screen and blank placeholder screens.

    scaffold

  4. Test

    Write scenarios on the original. A test is kept only if it passes there and fails on the blank screen.

    tester · haiku-4-5

  5. Build

    Rewrite each screen in React Native, in its own staging folder. Builders never see the tests.

    builder · haiku-4-5 → sonnet-4-6

  6. Gatekeeper

    Check every draft, promote it into the app, and roll it back if an older screen breaks.

    deterministic · no model

The Gatekeeper

Five gates, in order. The first failure goes back to the builder.

Every message names the file, the line and what is missing, so the next round fixes that one thing instead of starting over.

  1. 1parseThe draft is valid TypeScript. One syntax error would take down every screen.
  2. 2forbiddenApisNo div, window, localStorage or react-router-dom, with the React Native replacement for each.
  3. 3tscThe draft type-checks against the rest of the app.
  4. 4labelsEvery label and button name the tests use is in the code, copied from the original.
  5. 5scenariosThe tests pass on the phone build, then the tests of every promoted screen run again.
  6. 6androidExportThe app also bundles for Android, without a device.

What the report claims

Every screen gets one of four statuses.

proven

All tests pass on the phone, every obligation is covered, and every interactive element is tested or marked as not portable.

partial

All existing tests pass, but some obligation or element has no test yet. The report lists which.

unproven

The screen is in the app, but no validated test exists for it.

failed

Tests exist and the screen still fails them after its last round.

A screen with zero tests is never proven.

Check it yourself

Rerun the proof without a model or an API key.

$ npm run migrate:mock -- examples/todomvc

The whole flow with recorded model answers. Costs $0.

$ npm run verify -- output/<run-id>

Runs every saved test against the finished app again. Same result every time.

$ npm run sabotage -- output/<run-id> recipe-list

Breaks one screen on purpose, so you can watch verify catch it.

Built on Mozaik

Many small agents, one shared board.

  • Builders write only to their staging folder. An OwnershipGuard intercepts every write outside it before it happens.

  • Only the Gatekeeper writes to the app. Promotion is a copy, and rollback restores the exact previous files.

  • One loop per agent, fresh context per task. Parallel work comes from more builders and testers, scaled to the size of the app.

  • Events carry IDs. Plans, tests and results live on the board and on disk, so every run can be replayed and reported.

Team

Four people, four layers.

A

Contracts, runtime and the Conductor that hands out work and scales the team.

B

The test language, the tester agent, verify and sabotage.

C

The Expo template, scaffold, the builder agent and the Gatekeeper.

D

App analysis, the architect agent and the report.
